# Forge 1.7.10 compatibility

This module targets Minecraft 1.7.10, Forge 10.13.4.1614, and Java 17+ on a GTNH/RFB-style modern Java stack. The Java 17 `common` module is packaged in the distribution. Stock Java 8 Forge is not a target. Compatible Crucible setups need separate runtime testing.

RetroFuturaGradle's plain development server uses the stock Java 8 era FML/ASM discovery path and rejects this Java 17 mod before the entrypoint. The distribution instead boots through the GTNH RFB/lwjgl3ify stack described below. Crucible needs separate runtime testing.

## Native administrative operations

Inventory inspection uses native IInventory order: main inventory 0–35 (hotbar 0–8), armor 36–39 (boots through helmet), or ender chest 0–26. Empty/zero-sized stacks are omitted and the cursor is not an inventory slot. Inspection is read-only. Stack display-name failures are logged with player/slot context and fall back to the native item registry name. Common currently displays at most twenty occupied entries.

Repair uses the native stack/item damageability, damaged-state and damage setter APIs in place. Held-only repair inspects the selected main-inventory stack; all repair includes main/hotbar/armor and excludes ender/cursor. Counts reflect stacks actually repaired, including detecting an ignored mod damage setter. Changed inventories are marked dirty and synchronized through native containers/held-item updates. ItemStack identity, count, unrelated NBT and existing enchantments are retained.

Minecraft 1.7.10 has a registered `Enchantment.enchantmentsList`, not the modern Forge namespaced enchantment registry. Actual registered vanilla objects receive canonical `minecraft:` aliases. Every representable registered object receives `enchantment:<numeric-ID>`; unambiguous command-safe native names receive `enchantment:<native-name-without-enchantment-prefix>`. For example EnderIO's native name resolves as `enchantment:enderio.soulbound`; no guessed mod namespace is invented. Duplicate native names are omitted, retaining numeric resolution. Numeric IDs depend on the pack's enchantment configuration. Unknown enchantments, empty/incompatible hands and levels outside 1–255 return false. Native `canApply` validates targets; this is intentionally stricter than modern adapters' unrestricted stack-enchant operation. Common's configured high levels remain available. NBT levels are written as shorts, avoiding vanilla addEnchantment's byte truncation above 127; applying the same enchantment updates its entry rather than adding another. The generic platform suggestion capability preserves modern adapters' previous useful defaults.

`getHighestBlockY` returns the safe SUPPORT block Y, while RTP continues returning first-air feet Y. Common `/top` adds one. The shared conservative surface scanner rejects foliage, liquids, obstructions, insufficient height and roofed providers rather than inventing a safe surface there. `/jump` follows the live native look vector, preserves orientation and checks player-sized swept boxes at half-block intervals before exact same-world teleportation. It rejects solid obstruction, liquid, invalid height and unloaded chunks; it does not generate a corridor or pass through walls. Clear destinations may be in air and therefore fall under ordinary player physics. This controlled behavior is intentionally more conservative than modern endpoint-only jumps.

## Native locations and teleportation

World IDs are signed decimal Forge dimension IDs, for example `0`, `-1`, `1`, `7` or `-42`. Existing common string serialization is unchanged. These identifiers survive restart when the pack retains its dimension-ID configuration; changing a mod's assigned ID requires migrating its stored locations. Modern resource IDs and dimension display names are not guessed or silently mapped. Unknown/unregistered IDs fail cleanly. Loaded server worlds are resolved first; a registered unloaded dimension can be initialized by `MinecraftServer.worldServerForDimension` and its provider ID is checked before travel.

Same-world travel uses `NetHandlerPlayServer.setPlayerLocation`. Cross-world travel uses Forge's `transferPlayerToDimension` with a destination-specific native `Teleporter` that performs exact placement and never creates/uses a portal. Explicit placement overrides portal scaling; the native End departure path skips spawning, so the destination explicitly registers the player on that path. The final synchronized position retains the stored yaw/pitch, clears momentum/fall distance and dismounts a mount. Invalid/non-finite inputs, dead/offline players, missing dimensions and Y outside the destination's native height return false; the coordinate-only void overload safely does nothing on failure.

RTP inspects the requested column in the current world, obtains its chunk, and scans downward within native/provider height. The first non-air surface must be a full normal solid cube with two air blocks above and an unobstructed, non-liquid player-sized clearance box. Liquids, void, leaves/non-solid surfaces, collisions and height ceilings fail closed. Roofed (`hasNoSky`) providers are intentionally unavailable to this surface algorithm, avoiding Nether-roof/cave assumptions. `getHighestBlockY` shares this safe-surface search, returns the support block Y (feet Y minus one), and returns null for unsafe terrain; it is not a promise to find the highest arbitrary block. Synchronous chunk generation is bounded by the common RTP attempt count; no pre-generation sweep is performed.

## Moderation and early admission

The existing common BanCommand, TempBanCommand, IpBanCommand, MuteCommand, TempMuteCommand, WarnCommand and JailCommand are supported. Kick remains supported. Their catalog roots are `ban`, `unban`, `pardon`, `tempban`, `ipban`, `tempipban`, `unipban`, `mute`, `unmute`, `tempmute`, `warn`, `setjail`, `jail` and `unjail`. Each module uses its existing contributor, toggles, configuration and CommandAccess permissions. Disabling a command releases its native root; it does not revoke existing punishments. No platform-specific moderation commands or storage were added.

Forge/FML's normal player-login event occurs after admission and announcement. The focused `NetHandlerLoginServerMixin` injects at the HEAD of native `NetHandlerLoginServer.func_147326_c`, completes an incomplete profile with vanilla `func_152506_a`, and calls `MinecraftLoginHandler` with the resulting UUID and native socket address. A common PunishmentService login block invokes native `func_147322_a` and cancels acceptance before login success, the Forge handshake/player creation, announcements or common join listeners. Allowed logins continue through all native/mod admission checks. The ordinary common post-join guard remains a fallback.

The initial ServerConfigurationManager admission hook exposed a real full-pack conflict: ServerUtilities 2.2.2's `MixinNetHandlerLoginServer.serverutilities$skipMessageIfVanished` changes any admission rejection to null for players with `serverutilities.bypass_player_limit`. The final direct cancellation avoids that expression modifier; banned OP rejection was then verified before login success after restart. There is no ServerUtilities dependency or permission integration. The early loading plugin implements UniMixins' GTNH `IEarlyMixinLoader` and returns no ASM transformers. UniMixins is compile-only, not embedded. RFG's generated MCP-to-SRG mappings produce the packaged refmap. Required injection failure is fatal rather than silently dropping enforcement.

`Paradigm` binds the admission handler after `Services.setServer` starts the existing singleton PunishmentService, and clears it before service shutdown. Common owns cache loading, deterministic block selection, server/network scope, IP canonicalization/hashing, refresh scheduling, expiry, persistence, audit and events. Reads check `activeAt` even between refreshes. The native bridge does not perform database or Mojang HTTP lookups during admission. It uses InetSocketAddress.getAddress().getHostAddress() without a port or reverse DNS; unresolved/unknown socket addresses provide no IP identity. Rejection logs include punishment ID/type and no raw IP. Vanilla connection diagnostics can still include their normal address information.

BanScreenFormatter supplies both immediate and admission disconnect messages. Minecraft 1.7.10's native methods accept strings, so the adapter preserves legacy colors/decorations, newline-separated reason, actor, ID, expiry and appeal URL. `MinecraftComponent.toLegacyText` uses server-available style getters; vanilla getFormattedText/getFormattingCode are client-only and cannot be called on a dedicated server. Protocol clients verified the received text and codes; a graphical ban-screen layout and interactive links were not tested or promised.

### Shared moderation invariants and failure handling

BAN and IP_BAN retain independent immutable history records: scope and temporary/permanent overlap are legitimate, and exact-ID revocation affects only the chosen record. WARN remains one history record per warning. MUTE permits overlapping records; chat remains blocked while any applicable record is active. Cached feedback uses the existing deterministic precedence. Revoking or expiring one mute does not invalidate another.

`/unmute <player|punishment-id>` and `/unjail <player|punishment-id>` now use the same common revocation path. Player names and UUIDs resolve online or through stored offline profiles. Zero active matches produces controlled feedback; one is revoked; multiple matches list exact IDs and require selection. Exact IDs must have the right format, type, active status and server/network applicability. Wrong-type IDs cannot revoke arbitrary records. Successful exact-ID feedback identifies the record rather than claiming the player has no remaining punishment.

One current jail state per server/player names its associated JAIL punishment. `StoredJailState.punishmentId` is additive, with the previous constructor retained. SQLite and MySQL migration V14 add the association and a stable per-subject lock table. Released states are associated deterministically by matching creation time, then newest unrevoked matching record; locations and ledger history are preserved. Legacy overlapping records are not arbitrarily discarded. JSON stores the association and per-state location additively, retaining reads of older global-location data.

Commands and Dashboard use the same common replacement operation. A per-player service lock serializes jail, unjail and reconnect restoration locally. The service captures the current position and performs native teleport on the server thread before committing a new state. SQL locks a stable server/player row before reading, compares the expected previous state, then inserts the candidate ledger, replaces state and revokes superseded same-server records in one transaction. A conflicting writer fails instead of overwriting its winner. JSON commits those changes through one atomic file mutation with in-memory rollback on persistence failure. No SQL transaction or global punishment mutation lock is held while waiting for the native server-thread action.

Failed teleport creates no new punishment. Failed persistence preserves the old ledger/state and restores the current valid jail destination, including dimension and orientation; without a valid jail, it restores the original position. Exact-ID revocation clears state only when its association matches that record. Expiry cleanup compares the association and original timestamps so an old scan cannot delete a replacement. A record that expires during replacement is not falsely reported as revoked. Successful replacement publishes revocations only for records actually revoked and one creation event after commit; tested failures publish no successful replacement events. Natural expiry continues to use `activeAt` and cleanup; this milestone does not invent an expiry event.

Audit creation and revocation now retain COMMAND, DASHBOARD or SYSTEM origin explicitly. Warning escalation inherits its triggering warning's source. Creation/revocation audit entries retain actor, ID, type, target UUID/name, scope and result, using a masked IP hash rather than a raw address. Existing common event/audit infrastructure is used throughout.

### Final moderation correctness: escalation claims and jail reconciliation

Automatic warning escalation now has one durable cursor per `(networkId, subject UUID, normalized rule)`. A rule identity includes warning count and window duration in seconds: `3@7d`, `3@168h` and `3@1w` all become `3@604800s`. Ban duration, reason and textual window formatting do not reset the cursor. Changing the actual warning count or window duration creates a distinct policy that may immediately consume already-eligible warnings; removing and reintroducing an equivalent rule retains its consumed boundary. Existing escalation history keys are normalized when read, preserving previously consumed thresholds.

The evaluator counts warnings strictly after the window/history/cursor boundary, as before. A candidate includes the expected previous cursor and a forward consumption timestamp. SQL migration **V15** adds `moderation_escalation_claims`, with a primary key on network, subject and rule. MYSQL locks those stable rows in sorted order, checks the expected cursor, inserts the escalation ban and advances every eligible rule in one transaction. SQLite uses its existing serialized transaction boundary and the same primary key. A losing candidate returns an empty result without a punishment, creation event, audit creation or repeated escalation kick. Ledger insertion failure rolls the claim back. Later warnings can reach a new threshold and advance the cursor again. When multiple rules are eligible together, the existing harshest-ban selection remains, and all triggered rules are consumed together.

V15 uses additive `CREATE TABLE IF NOT EXISTS`; it does not rewrite existing punishment history or V14 jail associations. The existing database-owned migration lock protects simultaneous MYSQL startup. Tests cover V14 upgrade preserving history, first claim concurrency, subsequent claims, failed ledger insertion and retry. JSON persists cursors and the candidate through one existing atomic file mutation, with persistence-failure rollback. Its guarantee is **single-process only**, not cross-process shared JSON locking.

Jail restoration performs bounded reconciliation on join/restoration. An associated state whose punishment is missing, revoked, expired, the wrong type, another subject or outside the current scope is conditionally removed and is not teleported. Removal compares the exact inspected state under the existing subject lock, so it cannot clear a newer replacement. An active orphan JAIL record without a stored destination is retained for administrative review, logged when seen in the active cache, and does not invent a jail location. Compatible old unassociated states remain readable. This is not a global startup sweep or a transaction spanning native player movement and SQL.

Forge `ServerChatEvent` delivers chat listeners in registration order at `HIGHEST` priority. Forge can still have other listeners with their own priority. `CommandEvent` similarly delivers the common command guard for player commands and propagates cancellation. Focused early Mixins redirect the native `ServerConfigurationManager.initializeConnectionToPlayer` and `NetHandlerPlayServer.onDisconnect` announcement calls to `ServerConfigurationManager.sendChatMsg`. ## Chat/social semantics

Common chat composition is mute enforcement → StaffChat → GroupChat → Mentions. The native bridge stops on cancellation, and the generic module event gate also excludes cancelled chat. STAFF wins over GROUP through the existing ChatRoute and ordering. A routed message never reaches public mentions. Routed sender permissions are rechecked per message; losing permission cancels the pending private message and clears that mode, rather than publishing it. Logout clears StaffChat and GroupChat modes and pending group requests. Existing GroupChat membership/invitations remain in memory, not a new persistent store.

Ignore retains the common policy: it blocks private-message delivery only. It does not filter public, staff or group chat. SQL insertion now reports an already-present ignore as unchanged rather than deleting/reinserting it; other storage failures still propagate. PM reply links update both directions, are removed on logout, and SocialSpy excludes participants and rechecks recipient permission. Disable clears PM conversations/spy state. Mute blocks ordinary chat including toggled staff/group routes; it does not add a command-wide mute policy. Direct message commands retain their existing authorization and policy.

Mention titles and StaffChat persistent bossbars are omitted through generic modern-default-true capabilities. Direct title/bossbar adapter calls now have controlled chat fallbacks; capabilities remain false because there is no native renderer or safe persistent boss indicator. Mention chat and native sound remain active. `minecraft:entity.experience_orb.pickup` maps to `random.orb`; `minecraft:block.note_block.pling` maps to `note.pling`. Other valid native names or mod namespace IDs pass through without an invented exhaustive mapping.

First-join detection combines the native leave-game statistic with `PlayerPersisted.paradigmJoined`, written only after successful common join dispatch. First message replaces regular/native join, regular join replaces native join, and custom leave replaces native leave. Enabling only first-join formatting preserves native announcements on subsequent joins/leaves. Disabling both preserves native announcements. An early banned connection does not consume first-join state. Existing pre-port players with a nonzero leave-game statistic are treated as returning players.
